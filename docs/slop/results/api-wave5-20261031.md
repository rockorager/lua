# Embedding API, wave 5, 2026-10-31

Wave 5 added `Values`, raw table access, bound functions, `pcall`,
coroutines and yields, strict decoding, and a writer for `print`; made
`vm.pcallMsgh` report a status; and ported the standalone `lua` onto the
API (`../api.md`). Three questions: did the existing API paths get
slower, what do the new ones cost against the engine's own path, and is
the `lua` executable on the API as fast and as small as the one on the
engine.

## Method

Intel Xeon @ 2.60GHz (the orb's), Zig 0.16.0, ReleaseFast, every process
pinned to the last core with `taskset`, 10 interleaved rounds with the arm
order rotating, peak RSS from GNU time's `%M`, compared with benchstat.
The orb was noisy during these runs: spreads of 5 to 15% where wave 4 saw
2 to 5%.

- **API against wave 4**: the `api` arm of `bench/api` built from
  origin/main (`old`, 832668a) and from this branch (`new`), the seven
  scenarios both have, interleaved as `just bench-api` interleaves its
  arms, with the work checked equal.
- **New scenarios**: `just bench-api` on this branch. `lua_calls_bound`:
  Lua calls `add_to(1)`, a Zig function bound to a `*i64` with
  `State.function`, against a native closure with a light userdata
  upvalue. `call_values`: the host calls a Lua function returning three
  values and takes them as `Values`, against `vm.pcall` with all results.
  `zig_resumes`: the host resumes a generator coroutine, against
  `vm.resumeThread`.
- **The `lua` executable**: every `bench/` program on the reference, on
  `lua` built from origin/main (`old`, 832668a, on the engine), and on this branch
  (`new`, on the API), three arms interleaved in `just bench-compare`'s
  loop, checksums checked.

## Results

The API's existing paths cost what they did: geomean +0.3%, peak memory
equal. One scenario is significant, `zig_calls_lua` at +2.2% (0.6 ns,
p=0.005); its no-traceback twin is +2.0% and not significant, and
`globals`, whose code did not change, is −3.2% (p=0.035), so the residue
is at the size of the layout noise. An earlier build was 6.7% slower on
`zig_calls_lua`: `placeCall` made the function's value first and stored
it after the arguments, a 16-byte copy spilled across the argument
stores and read back from two narrow stores, the store-forwarding stall
`api.md` already warns about. Storing the function first when the
arguments are a tuple fixed most of it (+3.1%, then +2.2%); `Values`
arguments keep the old order, because borrowed values may sit where the
function goes. What is left shows in the profile as `vm.preCall`, which
did not change but now sits 130 KiB from `vm.call` (12.8% of samples
before, 15.2% after). Dropping kept `Values` (`dropKept`, three loads on
every call) measured nothing: a build without it against one with it, 15
rounds, `zig_calls_lua` +0.8%, p=0.62.

New scenarios, against the engine's own path in the same binary: a bound
function is 12.5% faster than the hand-written native closure (the same
exact-type decoding that makes `lua_calls_zig` 27% faster), `Values`
costs 4.9% (1.5 ns) more than `vm.pcall` with all results, and a resume
from the host is 5.3% (1.8 ns) slower than `vm.resumeThread`: the API
anchors the coroutine on the caller's stack, clears the trace, and
checks the coroutine's stack for the arguments, which the bare engine
call does not. Peak memory is equal everywhere.

The `lua` executable on the API is as fast and as small as the one on
the engine: geomean −0.26% wall time, no program slower (`patterns`
−4.3%, p=0.009, the rest not significant), peak RSS +0.01%, every
checksum equal. Against the reference both stay 29% faster and 24%
smaller.
