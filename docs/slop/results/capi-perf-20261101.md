# Wave 12: C call cost and `read("a")` in the C-API build, 2026-11-01

Two gaps the C-API build had against reference 5.5.1 after wave 11:
`file:read("a")` took 1.6× the reference's time, and a call from Lua to
an empty C function cost about 4.5 ns more than the reference's (a C
function calling back into Lua with `lua_call`, about 10 ns more). The
design is `../c-api.md` ("Errors: protected calls into C", "aarch64",
`capi.Box` under "The rest"). Machine: the orb's 4-core Intel Xeon @
2.60GHz, kernel 6.1. Runs pinned to core 3 with `taskset`, every arm
under 16 environment sizes (a `PAD` variable of 0 to 3840 bytes, which
moves the stack: single programs move up to 9% with it), arms rotated
within each size, benchstat. Builds are ReleaseFast. Base is 8ed7529;
`ref` is the dev shell's `lua`.

## Headline

- `read("a")` of a 20.6 MB file, 20 times: base +60.9% time against the
  reference, now −6.6%; peak RSS 63.0 MiB (reference 63.3) to 42.9
  (−32.2%). Page faults 202k to 101k, the reference's 101k.
- io geomean against the reference: base −17.2% time, now −27.5%; peak
  −12.3% to −15.9%. Every io workload is faster than the reference:
  write −52.6%, lines −30.6%, `read(5)` with `read("n", "n")` −31.5%,
  `read(4096)` −7.6%, `io.write` −25.5% (base: −51.3, −28.8, −27.2,
  level, −19.2).
- An empty C function, a loop iteration: base 15.23 ns against the
  reference's 10.75 (+41.7%), now 11.10 (+3.3%). Net of the loop (4.67
  ns for the reference, 4.08 and 4.11 for ours) that is 11.15 ns
  against 6.08, now 6.99: the gap from 5.1 ns to 0.9. `add` (two
  checked integers in, one out): +18.7% to +3.0%.
- C → `lua_call` → Lua: base 47.71 ns against 37.63 (+26.8%), now 43.06
  (+14.4%).
- Native stack per C → `lua_call` → Lua level: 672 bytes to 608 (the
  budget is 656; the reference 351). The 192 KiB limit and the 256 KiB
  guarantee are unchanged; capitest's 300-deep nesting stops at "C stack
  overflow" as the reference does.
- The default build is unchanged: `.text.hot`, `.text`, and `.rodata`
  byte for byte base's (`objcopy -O binary --only-section`, `cmp`).
- What it cost the C-API build elsewhere: bench/ +1.45% time geomean
  against base (coroutines +7.8%, fib +2.0%, template +1.8%, the rest
  `~`), +0.5% peak RSS; text +6.9 KB; the floor (`lua -e ''`) 1900 KiB
  to 1932 (the reference 2612).

## `read("a")`: the box becomes the string

liolib.c's `read_all` reads into a `luaL_Buffer`. Its box, after wave
11, was a block from the state's heap that grows in place, and
`luaL_pushresult` copied it into a new string: for a 20.6 MB file, a
second fresh map of the same size, faulted in page by page, then the
box's freed. Each read faulted twice the file's size in. 5.5.1 makes
the box an external string instead (`luaL_pushresult` with
`lua_pushexternalstring`).

The box now allocates from the state's string allocator
(`heap.rawStrings()`), aligned as a `String`, with room for a `String`
header before the bytes. `Box.toString` shrinks the block to
`String.allocSize(n)` (in place: the tail is unmapped) and
`String.adoptLong` makes it a long string. `lauxPushresult` uses it
when the buffer is in its box and the result is long (over 40 bytes);
a short result is interned by copy as before.

```
perf stat -e minor-faults -r 3, io.lua all (20 × read("a") of 20.6 MB)
ref    101008 faults   410.9 ms task-clock
base   202072 faults   544.8 ms
new    101154 faults   285.7 ms
```

## C calls: one protected region per loop entry

Wave 11 called every C function through `capi.trampoline`, a native
whose body made a protected call (`jmp.call`, a naked function saving
the eight callee-saved registers and the return address) and checked
its result. `results/lean-20261031.md` measured the protected call at
2.6 ns and `callNative` at 2.8 ns of the empty call's cost.

Three changes:

1. **`jmp.call` is inline assembly** in its caller. It stores the stack
   pointer and the frame pointer (on aarch64 also the resume address,
   `adr`), calls the function, and declares every other register
   clobbered, so the compiler keeps nothing live in a register across
   it and `jump` restores only those two. x86-64: the call is made
   16-byte aligned (`andq $-16`), the old stack pointer kept in r12, and
   the `int` result zero-extended by a 2-byte `movl %eax, %eax` that
   `jump` skips by resuming at the pushed return address + 2. The
   compiler does not see a call, so C-API builds have no red zone
   (`build.zig`); skipping 128 bytes in the assembly instead cost 128
   bytes of stack per level.
2. **The interpreter loop runs inside one protected region per entry.**
   In C-API builds `vm.execute` is `capi.protectLoop`: it links a
   `Catch` into the thread-local chain and makes one protected call of
   `loopEntry`, a C-convention wrapper of the loops that returns their
   error as an integer. `CALL` and `TAILCALL` call natives through
   `callNativeDirect`, whose C functions run unprotected
   (`capi.callCDirect`); a raising C function jumps to the region, past
   `callNativeIn`, `runLoop`, and `loopEntry`, which return errors by
   `try` alone, and `protectLoop` returns the stored error, which is
   what the error's return through them would have given. Natives
   called any other way still get a protected call each:
   `vm.callNative` inlines `capi.callC`, the trampoline's body, so
   there is no trampoline frame either.
3. **`callYieldable` sends a Lua callee straight to the loop** in C-API
   builds (`pushLuaFrame`, `fresh`, `execute`), skipping `preCall`'s
   dispatch: −1.1 ns on the callback.

Smaller: `luaPushvalue` and capi's `get` copy a value field by field,
as the loop's `MOVE` wrote it (a whole 16-byte load after two narrower
stores fails store forwarding).

### The invariant

`unwind.zig`'s check now covers the region (`checkRegion`). The chain
from the region to the C call is `loopEntry` (capi.zig), `runLoops`,
`runLoop`, `callNativeDirect`, `callNativeIn` (vm.zig), `callCDirect`
(capi.zig). Each must exist and have no `defer` or `errdefer`; each but
`loopEntry` calls the next only right after `try` or `return`, where an
error would have gone straight through it anyway; and each is named
only by the one before it (`callNativeIn` also by `callNative`, which
passes the protected `callC`), with `execute` allowed to name `runLoop`
only if its body opens with `if (comptime lua_options.c_api) return
capi.protectLoop(th);`. A seeded test breaks each rule once. Changing
`runLoop`'s `try callNativeDirect(...)` to `callNativeDirect(...) catch
|e| return e` fails `zig build test -Dc-api=true` with "runLoop calls
callNativeDirect other than with try or return, inside the protected
region".

`jmp.zig`'s tests keep 24 values live across a protected call to a
function that overwrites every callee-saved register and the frame
pointer, moves the stack pointer down 256 bytes, and jumps; another
checks a returning call's `int` (-1) comes back zero-extended. Without
the frame pointer's restore in `jump` they crash in Debug, ReleaseSafe,
and ReleaseFast.

### Clobbers LLVM drops

Two clobbers did not do what they said, both found by testing:

- aarch64: Zig passes `~{x30}` through, and LLVM ignores it. It kept a
  pointer in x30 across the call (`str x10, [x30, x11]` after the
  `blr`), and every C-API test segfaulted under qemu. `.lr` (LLVM's
  name) works: the qemu trace of `callNative` and `callYieldable` after
  the call has no x30-based access.
- x86-64: a clobber of a register class the target lacks is dropped.
  On this AVX-512 orb `~{zmm8}` covers xmm8, but compiled for
  `-mcpu=x86_64` or `x86_64_v3` a double stayed in xmm1 across an
  assembly block clobbering zmm0 to zmm15 (and in xmm17 on v4, outside
  the clobbered zmm0 to zmm15). The clobbers now name xmm0 to xmm15,
  ymm0 to ymm15, and zmm0 to zmm31; with them the value is spilled on
  all three CPUs. `zig build test -Dc-api=true -Dcpu=x86_64` passes.
  The AVX-512 mask registers and the x87 stack have no names in Zig's
  clobber set; nothing around a call holds them.

### Where the callback's remaining 5 ns go

perf on `callback` (20M calls): `runLoop` 61% (the outer loop with its
`CALL` and the callee's five instructions), `callYieldable` 15%
(mostly the dependent loads from the stack slot to the closure to the
prototype's frame size, and the `enterNative` C-stack check),
`callNativeDirect` 8%, `lua_pushvalue` 6%, `loopEntry` 4%, `lua_callk`
3%. The region itself (the chain's two thread-local stores, the
protected call, `loopEntry`) is about 1.8 ns a callback; the reference
pays a `setjmp` only in `lua_pcall`. A whole-value copy in `SETUPVAL`
(`Upval.set`, through a stack temporary in overlapping stores) stalls
on store forwarding; a C-API-only field-by-field `SETUPVAL` removed the
stall from the profile but not from the time (42.50 against 42.59 ns,
16 sizes), as the cost moved to the next `GETUPVAL`'s load of the same
upvalue, so it was dropped.

### What the region costs where the loop is entered often

A coroutine's loop needs its own region, so every resume enters one:
ping-pong resume and yield went from ~61 to ~67 ns a round trip
(bench/coroutines +7.8%). perf puts it in `loopEntry`, the error's
return through `loopFailed` for the yield, and `unroll`, which holds
the inlined region and keeps nothing in registers across it. Making
`protectLoop` a function of its own instead of inline did not help
(~70 ns) and took the stack per level to 656 bytes.

fib and template, which call no C, are +2.0% and +1.8%. Not layout:
the unhooked `runLoop` is 1252 bytes longer (0x7224 to 0x7708) and its
register allocation moved (the program counter in r10, caller-saved,
instead of rbp; its five `memset` calls gone). Its source differs from
base only in `CALL` and `TAILCALL`, and building with them calling
`callNative` as before, or without the `callYieldable` fast path, or
with the red zone back, leaves it at 0x7708: the shift comes from
outside `runLoop`'s source and was not pinned down.

## The default build

`objcopy -O binary --only-section` of `.text.hot`, `.text`, and
`.rodata` from the default ReleaseFast build, compared with `cmp`
against base's: identical, with the regenerated `src/order.ld`. The
default build's `execute` keeps its loop; `callNative` passes `{}` for
the C call it never makes; `vm.zig`'s other C-API code is behind
`comptime lua_options.c_api`.

## Rejected

- **Arming the region lazily**, linking it into the chain only when the
  loop calls C: moves the thread-local stores from each loop entry to
  every C call; a callback enters once and calls C as often.
- **A catch slot per thread or state** instead of the thread-local
  chain: a C function may raise on a `lua_State` other than the one
  whose loop is running (a coroutine it resumes), and the jump must
  reach the innermost protected call on this OS thread.
- **Skipping the red zone in the assembly** (`subq $128, %rsp`): 128
  bytes of native stack per C → Lua level.
- **Saving no registers but keeping `call` a naked function**: no gain
  over the old pair; the saving comes from not making the call at all
  for C functions the loop calls.
- **`SETUPVAL` field by field** and **`protectLoop` out of line**, above.
