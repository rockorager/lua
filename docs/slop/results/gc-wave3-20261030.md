# The wave-3 collector: speed and peak memory, 2026-10-30

What porting lgc.c (`../gc.md`) did to speed and peak memory. Base is
`main` at 284484d (the wave-1 stop-the-world collector: a full collection
whenever the heap doubled, at least 256 KiB, no barriers). New is the
`wave3-gc` branch: incremental and generational modes with 5.5's default
parameters, real barriers, and the standalone `lua` in generational mode
as lua.c runs it. Ref is the dev shell's C Lua 5.5.1.

## Method

`zig build -Doptimize=ReleaseFast` of each tree. Fifteen rounds, the three
arms interleaved in a rotating order, pinned to core 3 with `taskset`,
whole processes, wall time from bash's `EPOCHREALTIME`, compared with
benchstat. Peak RSS is GNU time's `%M`, the median of five runs, pinned
the same way (see "Measuring RSS" for why pinning matters). Instruction
counts are callgrind's `Ir` on `-Dcpu=x86_64_v3` builds with smaller
inputs (`binary_trees 12`, the others at 20000). The orb is shared and
other jobs ran on other cores, so wall-time spreads are around 10%; the
instruction counts are exact.

The barrier checks inlined into `SETTABLE`, `SETFIELD`, `SETI`,

## Peak memory

Peak RSS in KiB, median of five pinned runs:

| Program        |   Ref |  Base |   New | New / ref |
| -------------- | ----: | ----: | ----: | --------: |
| `binary_trees` | 31560 | 18972 | 27404 |     0.87× |
| `hash_string`  | 22600 | 34744 | 25552 |     1.13× |
| `hash_int`     |  8480 | 12112 |  5992 |     0.71× |
| `array`        | 35432 | 20900 | 20924 |     0.59× |
| `table_concat` | 40488 | 22184 | 43572 |     1.08× |
| `patterns`     | 17668 |  8752 |  9896 |     0.56× |

Small programs stay at the process baseline, 2.4 MB against the
reference's 2.9 MB.

- `hash_int` (1.43× → 0.71×): base collected only when the heap doubled,
  so a table deleted and rebuilt waited a whole doubling. With 5.5's
  pacing it is collected in a few minor collections. Where natives check
  the collector matters: checking after every native return made a minor
  collection run inside the `pairs` loop, so a table that was about to
  die aged first and waited for the next major one (9.0 MB). Checking
  only after natives that allocated gives 6.0 MB. Table sizing was not
  the cause: the collector change alone takes it under the reference.
- `hash_string` (1.54× → 1.13×): the collector part is fixed; the rest
  is not the collector and not table sizing. Our `String` header is 40
  bytes before the contents (the reference's `TString` is 24), and
  `smp_allocator` rounds every allocation up to a power of two, so a key
  such as `"key12345"` takes 64 bytes (40 + 8, rounded) against about 48
  in glibc's malloc for the reference's 24 + 9. The generational major/minor
  decision also differs because the reference's `..` with a number
  argument builds a garbage string for the number and ours does not, so
  the two heaps cross `minormajor` at different times. An incremental
  step that pays for the whole debt (`../gc.md`, "Modes and parameters")
  took it from 31.7 MB to 25.6 MB.
- `binary_trees` (0.60× → 0.87×): stop-the-world collection at twice the
  live heap kept less than generational mode with `minormul` 20 does, but
  it stays under the reference.
- `table_concat` (0.55× → 1.08×): with only a check when a native returns,
  generational mode stayed in major collections with a 250% pause,
  because the live bytes at the decision landed 0.1% under the
  minor/major limit (15 685 146 against 15 699 644, traced). It peaked
  at 63.4 MB. The reference's `luaL_Buffer` checks the collector each
  time it grows; `table.concat` now checks after each piece, which gives
  43.6 MB, with no measurable cost (the A/B above). What is
  left is the 4 MB result strings, which both keep twice (buffer and
  string) at the end of each `concat`; not traced further.

### Measuring RSS

Unpinned peak RSS is not reliable for our binary. Zig's `smp_allocator`
gives each thread a slot of slabs, and when a slab runs out it rotates
the thread to another slot (`std/heap/SmpAllocator.zig`), so even a
single-threaded program can spread its memory over up to `cpu_count`
slots' partly used slabs when the scheduler moves it between cores.
Every number above is pinned with `taskset` to rule that out; unpinned
runs of the final binary on a quiet core agreed with the pinned ones to
within 0.1 MB (`hash_string` 25.6 MB, `binary_trees` 27.5 MB), so it did
not move these numbers, but a busy machine could. The standalone `lua`
would behave the same in production, so the allocator choice in
`main.zig` is worth measuring on its own.
