# Copying values field by field, 2026-10-30

After the operand change (`vm-operands-20261030.md`), spectral_norm's
profile showed 7% of samples on one instruction in `RETURN1`'s result
copy: a 16-byte vector load of the result, which `DIV` had just written
with two narrower stores (the 8-byte float, then the 1-byte tag). Store
forwarding cannot serve a load that spans two stores, so the load waited
for both to retire. A Zig struct assignment of `Value` compiles to that
16-byte copy everywhere: `MOVE`, results, upvalue reads.

## The change

`vm.put` and `vm.setv` copy a value's payload and tag as two separate
moves, as PUC-Rio's `setobj` does, and the hot copies use them: `MOVE`,
`GETUPVAL`, the `GET*` results, `SELF`, `TESTSET`, a tail call's
arguments, and `moveResults` (every return). A narrower load out of a
wider store forwards, so the order of writer and reader no longer
matters.

Base is `wave3-perf` at 2ce4506; new is this change. Both ReleaseFast,
10 rounds of every `bench/` program, interleaved in a rotating order,
pinned to the last core with `taskset`, wall time and peak RSS per
process, benchstat. (This was one arm of a three-arm run; the third arm,
the table change, has its own write-up, `vm-table-access-20261030.md`.)

## Reading it

- spectral_norm −9%, array −6%, nbody −5%, mandelbrot −4%, closures
  −4%: the programs that return computed values or move them between
  registers.
- format and patterns +0.6% and +1.2% are code layout; neither runs the
  changed copies on its hot path, which is in the string library.
- Peak RSS is unchanged.
