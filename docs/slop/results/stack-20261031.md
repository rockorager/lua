# Native stack per C level, and a byte limit for "C stack overflow", 2026-10-31

The fuzz campaign (`fuzz-20261031.md`) measured 2 to 5 times the
reference's native stack at the 200-level C-stack limit, and the C API
prototype 1903 bytes per C → Lua level against the reference's 351, 1432
of them `vm.runLoop`'s own frame (`c-api-20261031.md`). A host thread of
256 KiB crashed on a hostile script instead of raising "C stack
overflow". This wave cut the frames on those paths and made the limit
count bytes as well as levels.

Headlines, ReleaseFast:

- `vm.runLoop`'s frame: 1504 bytes to 288 (the hooked instance 1488 to
  272).
- Native stack at the C limit, as the smallest `ulimit -s` that runs
  the script with its full output: `pcall` recursion 400 KiB to 135 (the
  reference 182), `table.sort` comparators 618 to 176 (128), nested
  `__close` 356 to 112 (84), the parser 79 to 188 KiB to 56 to 167
  (49 to 124). Per level: `pcall` 1883 bytes to 512 (755), `sort` 3025 to
  728 (478), `__close` 1663 to 395 (250); the C API's C → Lua level 1903
  to 656 (351).
- "C stack overflow" fires by native stack bytes too: every hostile
  script of the campaign raises a Lua error on a 256 KiB host thread
  (`fuzz repro grammar FILE --stack 256`), down to 208 KiB; on the base
  build 18 of 31 crash. The reference itself segfaults on 5 of them
  with `ulimit -s 256`.
- Time: the bench/ geomean −3.1% against the base build, no program
  slower; peak RSS −10.5%, nearly all of it the dropped signal stack
  (below). The embedding API's calls into Lua −4.3% (its internal
  arm −15.6%).
- Release builds of `lua` drop Zig's segfault handler and its 256 KiB
  thread-local signal stack: `lua -e ''` peaks at 1216 KiB instead of
  1480 (the C-API build 2688 instead of 3008; the reference 2524).

## Where the stack went

LLVM gives a stack slot to every `alloca` it cannot promote to registers,
and two allocas share a slot only when their lifetimes are marked. Zig's
code had three kinds of unpromotable allocas, each repeated per call site
in the interpreter loop's 85 handlers:

- error unions and optionals with payloads are returned through memory:
  `?i64` from `toIntStrict`, `Error!bool` from `equalSlow`, `?Value`
  from table lookups, and every `Error!u32` or `Error!?Value` a slow path
  returned;
- inline functions whose `return` statements choose between values
  (`return if (n) |x| x.value() else .nil`) make LLVM select between the
  values' addresses, which SROA cannot split;
- 16-byte `Value` arguments to out-of-line calls are copied to a
  temporary at each call site.

In the base build the loop's 1504 bytes were about 80 such slots, none
shared. Moving cold code out of line does not help by itself; the slots
are in the loop's frame because the calls that need them are in the
loop.

## The changes

In `vm.zig`, the loop's slow paths take and give values by pointer:

- `toIntStrict(v, *i64) bool`; `equalSlow`, `orderSlow`, and `forPrep`
  write their result through a pointer; `getSlow`, `setSlow`,
  `arithSlow`, `lenSlow`, `concatValues`, and `preCall` return
  `Error!void`, and the loop tells a pushed metamethod frame by
  `th.frames.items.len > depth`.
- A constant operand of a slow path goes through one `tmp` Value, and a
  comparison's result through one `flag` bool, shared by every handler.
- `debuginfo.Origin`, the description of a value in a type error, is a
  `packed struct(u64)`, built with `.slot(x)`, `.upval(x)`, and `.none`.
- `Table.setIntAt` and `setIntHash` take the value by pointer; `getInt`
  and `getShortStrCached` build their result from one payload and one
  tag variable. `getShortStr` keeps its plain form (below).
- `GETVARG` passes the instruction to `getVarargs`; `ERRNNIL`'s error
  went to a cold `globalDefined`.
- Cold and out of line: `protectedCall`'s error branch (`recover`),
  `nativeOverflow`, `Thread.runError`, `errorInErrorHandling`, and the
  argument and type errors of auxlib, debuginfo, base, and coroutine.

In the libraries:

- `table.sort`: the `Sorter` methods take `*const Sorter`; `less` is out
  of line and calls the comparator itself; the `#t` with `__len` that
  sizes the sort is a separate function. `table.sort` 496 bytes to 160,
  `Sorter.sort` 816 to 128.
- `string.gsub`: the pattern engine's `gsub` stays out of line; 2672
  bytes to 2048. The rest is `auxlib.Buffer`'s 1 KiB of inline storage
  and the matcher's 32 captures, the reference's `LUAL_BUFFERSIZE` and
  `LUA_MAXCAPTURES`.
- auxlib's checks that do not inline take `*const Args`.

In the compiler:

- `subExpr` calls the code generator's `prefix`, `infix`, and `posfix`
  with `@call(.never_inline)`, and `suffixedExp`'s loop is a separate
  `suffixes`: their locals are no longer in every level's frame.
- `recField` is out of line, so its three expressions are not in
  `constructor`'s frame at every level of list nesting (368 bytes to
  160).
- `ExpDesc` holds its integer, float, and string constants in one
  `extern union`, as lparser.h's `expdesc` does: 64 bytes to 40.
- The parser's error functions are cold and out of line.

Readings move by a few KiB between runs. `pcall` now needs less than
the reference. `sort` (728 bytes a level against 478) and `__close`
(395 against 250) are 1.5 to 1.6 times the reference's: of each level, the loop's 272 bytes and the native call's
80 are most of it, where `luaV_execute` keeps its state in registers.
`p_funcs` is `body`'s `FuncState`, which holds seven growable lists (the
reference keeps them in the `Proto`).

`gsub` is the exception, and a divergence: its levels still cost about
2.6 KB (4.3 on the base build) against the reference's 2.05, so the byte limit stops it at 74
levels (72 in ReleaseSafe; 34 in cstack.lua's `gsub` with a metatable)
where the reference reaches 197, needing 431 KiB to do it. A script that
nests `gsub` callbacks 75 deep gets "C stack overflow" here and runs on
the reference with its 8 MiB main stack; on a 256 KiB thread the
reference segfaults instead.

The C API's stack per C → `lua_call` → Lua level, from `just bench-capi`:
656 bytes against the reference's 351 (wave 8: 1903). The rest of
`bench-capi`'s output is in `bench-compare-wave9-20261031.md`.

## The byte limit

`Thread.max_native_stack` is 192 KiB (4 MiB in Debug, whose frames are
several times larger). At an outermost entry into Lua — `enterNative`
when `native_calls` becomes 1, `resumeThread` from the host, and
`Parser.compile` with no Lua running — `State.markStack` records
`@frameAddress()` minus that budget in `State.cstack_limit`; a host may
call in from any depth or any thread, so each outermost entry marks
again. `enterNative`, `Parser.enterLevel`, and `resumeThread` raise
"C stack overflow" when the frame address is below the mark
(`State.nearStackLimit`), as they do at 200 levels. As with the level
count, a message handler for that error gets room past the limit, a
tenth of the budget (`State.cstack_handling`), and beyond it the error
becomes "error in error handling". The collector skips finalizers within
a hundredth of the budget of the limit, as `luaD_checkminstack` skips
them near the level limit. `os.exit` inside a nested call keeps the
host's mark (`closeState` lowers `native_calls` to at most 1, not 0).

With 192 KiB a host thread needs about 208 KiB in ReleaseSafe for every
hostile script; at 192 KiB nine crash (concat, format, gsub, gsub_table,
insert, load, sortlt, tostring, unpack), the paths that reach the byte
limit. A limit in bytes alone would have to assume the frames of the
deepest path; counting both keeps the reference's 200 levels everywhere
the stack allows them.

### 256 KiB host threads

`zig-out/bin/fuzz repro grammar FILE --stack 256` (a Zig thread with a
256 KiB stack), ReleaseSafe, for the 31 hostile scripts (`pcall`,
`xpcall`, `error` in handlers, `coroutine.resume` and `wrap`, `gsub`,
`gmatch`, `sort`, `tostring`, `string.format`, `table.concat` and
`insert`, `select`, `unpack`, `load`, `__close`, `__concat`, ipairs with
`__index`, and the parser's nine nestings):

- base: 18 crash (close, concat, coresume, cowrap, format, gsub,
  gsub_table, insert, ipairs, load, pcall, select, sort, sortlt,
  tostring, unpack, xloop, xpcall);
- new: none; each raises "C stack overflow", "stack overflow", or "error
  in error handling", or completes.

The standalone `lua` under `ulimit -s 256`, ReleaseFast and ReleaseSafe
without the segfault handler (below), gives the same results; the
reference, under the same limit, segfaults on concat, format, gsub,
gsub_table, and load.

## The segfault handler and signal stack

`std.Options` gives every executable a 256 KiB thread-local signal stack
(`signal_stack_size`) and, in safe builds, a SIGSEGV handler that prints
a stack trace from it. Release builds of `lua` set
`.enable_segfault_handler = false` and `.signal_stack_size = null` in
`main.zig`; Debug keeps both. The options belong to the executable's
root, so the library, the embedding API, `bench-api`, the examples, and
the fuzz driver are unaffected (`rg std_options` finds only
`main.zig`). The `TLS` segment of `lua` goes from 0x4001c bytes to 0x1c.

The C-stack and stack overflow paths raise Lua errors without it: the
31 scripts above under `ulimit -s 256`, and `local function f() return
1 + f() end print(pcall(f))` ("stack overflow"), on ReleaseFast and
ReleaseSafe.

The floor, `lua -e ''`, the smallest of five runs with GNU time under
`taskset` (KiB):

| ReleaseFast            | 1480 | 1216 |

| ReleaseSafe            | 1828 | 1564 |

No program is slower. array is 20% faster, steady across four full
runs (−2.3% in the first, before the `Table.get` fix below; −20.2%,
−19.3%, and −20.1% after); it is not traced to one change, and its integer-key
stores now pass the value by pointer (`setIntAt`). Peak RSS is the
floor's 264 KiB less in every program.

The first full run of the change was level on the geomean (−0.43%) but
methods +9.6%, oop +7.1%, and hash_string +9.6%, confirmed over 15
rounds. Two causes, found with `perf record -e cpu-clock` (the orb has
no hardware counters), and a third on the API's path below:

- `Table.get`, which `getSlow` calls, built its result in a stack
  temporary written in pieces (8, 1, 4, and 4 bytes) and copied it out
  with one 16-byte load, which stalls store forwarding; its samples
  doubled. It now returns the payload and tag field by field, and
  `getSlow` stores the result with `setv`. Its frame went from 144
  bytes to 32. methods and oop came back level.
- `getShortStr` with one payload and one tag variable made `GETTABLE`
  load the tag through a pointer chosen between the node and the array
  part, after the merge; hash_string, which is that load's cache misses,
  stayed 3 to 10% slower. Its plain conditional return costs `runLoop`
  32 bytes of frame (256 to 288) and brings hash_string level.

The embedding API's calls into Lua came out 8 to 11% slower than the
base build (`bench-api`'s `zig_calls_lua`, `zig_calls_lua_notb`,
`call_values`, api arm). `enterNative`'s new test for the outermost
entry (`native_calls == 1`) let LLVM read the 16-bit count with a 32-bit
load, across the 16-bit store of the previous call's decrement: a store
forwarding stall on every call from the host, 60% of `callYieldable`'s
samples. With the level check first the load is a `movzwl` again. Base
against the change, both arms of `bench-api`, 10 interleaved rounds on

## What it did not do

- `runLoop` is still 272 to 288 bytes, about twice `luaV_execute`'s.
  The remaining slots are values that live across calls in many
  handlers; the next step is to find which, from the IR's allocas
  (`/tmp/stk/allocas.py` lists them with their source lines).
- `gsub`'s levels (above), and `FuncState`'s lists in the parser's
  `body`.
- The store-forwarding stall above is a pattern to look for wherever a
  `Value` is built from fields and copied whole. The embedding API has
  one in its global and `Ref` reads (`refValue`), on the base build too:
  half of `main.main`'s samples in `bench-api api zig_calls_lua`, which
  is why that arm gained 4% here where the internal arm gained 25%.
