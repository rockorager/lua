the counts are lower than one run alone would reach. Each line is one

## Loader messages that differ from the reference

`binary-diff` (c4, 676,400 inputs) found the loader rejecting a corrupt
chunk with "truncated chunk" where the reference reads further and gives
another message. Both are "bad binary format"; ours checks a count against
the bytes left before reading the items:

| Reference                                               | Ours                                  |
| ------------------------------------------------------- | ------------------------------------- |
| `bad binary format (invalid constant)`                  | `bad binary format (truncated chunk)` |
| `bad binary format (invalid string index)`              | `bad binary format (truncated chunk)` |
| `bad binary format (integer overflow)`                  | `bad binary format (truncated chunk)` |
| `bad binary format (bad format for constant string)`    | `bad binary format (truncated chunk)` |
| `not enough memory` (a huge count it tries to allocate) | `bad binary format (truncated chunk)` |

`undump.zig` is outside this wave's files; these are reported, not changed.

## The driver's own false findings

- The first `oom --gc-stress` attempt flagged "state unusable after the
  failure" for `test/diff` programs. Those programs fail on their own in
  the sweep's state (no `os` or `debug` library) before the Nth
  allocation, and the sanity chunk run after them then took the failing
  allocation. The driver now skips the sanity run when no allocation
  failed. The same run's signatures were the child's first line, a
  progress line; they are now its last line, the outcome.
- The c3 `grammar` hangs: a generated `while` whose counter the body
  reset, and gc-stress runs over the 5 s limit. The generator's risky
  loops now end in `do break end`, timeouts scale by 6 under stress, and a
  hang is dropped when the reference also exceeds the limit.

## A/B: the length hint and the stack-move fixes

The fixes to `vm.zig` (`getSlow`, `arithSlow`, `lenSlow`,
`protectedCall`) touch only slow paths, and `Table.resize`'s hint is one
store either way. Base is ecce453, new is this branch, both ReleaseFast,
every `bench/` program, interleaved and pinned to the last core
(`taskset -c 3`) with the arms' order rotating each round, as
`just bench-compare` does; nothing else ran on the orb.

Headline: geomean +0.51% time (no program outside noise but `format`
+2.96% and `mandelbrot` +3.52%), +0.00% peak RSS. A second run of the
four programs nearest the line, 25 rounds: `format` and `coroutines` no
difference, `mandelbrot` +2.83%, `array` −1.95%.

`mandelbrot` runs no metamethod and resizes no table, so it does not
reach the changed code. `vm.runLoop` is the same 0x7dee bytes of the
same instructions in both binaries (an `objdump` diff differs only in
rip-relative offsets): the slow paths came out a few bytes shorter, so
the loop starts 32 bytes earlier (0x1045cf0 against 0x1045d10, at 48
mod 64 instead of 16). The `mandelbrot` and `array` shifts, in opposite
directions, are that alignment, not the fixes.
