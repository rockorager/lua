# Strings: a 32-byte header and size classes of their own, 2026-10-30

hash_string was the last program whose peak RSS stayed above the
reference's after the collector merge (25,512 KiB against 22,584). Its
live data is 200,000 short strings ("key1" to "key100000", "absent1" to
"absent100000") and one table at a time. The strings explain the gap:

```
                     header   "key12345" block (header + 8 bytes + zero)
reference TString    24 B     33 B, 48 B from glibc malloc
ours, before         40 B     49 B, 64 B from SmpAllocator's power-of-two classes
```

200,000 strings at 16 bytes more each is 3.2 MB, the whole gap.

## What was measured first

- A general size-class allocator for every object: rejected, it cost
  call-heavy programs 20–30% (`allocator-20261030.md`).
- Open addressing for the interner, which drops `hnext` and gives a 32-byte
  header without touching the length field: hash_string's peak went _up_
  (33,648 KiB with the small-block allocator below). Linear probing must
  stay under about 75% full, so 200,000 strings need 524,288 slots (4 MB)
  where chaining needs 262,144 buckets, and the doubling holds both arrays
  at once.

## The change

- `String` takes PUC-Rio's `TString` layout: after the 16-byte object
  header, `extra`, a one-byte short length, the hash, and a union of a
  long string's length and a short string's intern link. 32 bytes, down
  from 40 (the remaining 8 against the reference are our object header's
  padding). `len` becomes a method (`tsslen`).
- `State.Options.strings` names an allocator for strings and the string
  buffers that become them; `gc.Heap.stringAllocator` counts its bytes
  like the main one.
- The `lua` executable passes a `SmallAllocator`: size classes 8 bytes
  apart up to 128 bytes, carved from 64 KiB chunks, no lock; larger blocks
  go to SmpAllocator. "key12345" now takes 48 bytes. Nothing but strings
  uses it, so no closure, prototype, or array changes place.

Base is the buffer change (607da24); new is this change. ReleaseFast, 10
rounds of every `bench/` program, interleaved, pinned to the last core,
wall time and peak RSS per process, benchstat.

## Reading it

- hash_string's peak RSS drops 12.3%, to 22,384 KiB against the
  reference's 22,584 (its peak in the baseline run), and it runs 8.8% faster:
  interning allocates without SmpAllocator's lock.
- binary_trees −2.7% and patterns −3.5%: their strings shrink too.
- The small allocator's first chunks cost up to 48 KiB on programs with
  few strings (hash_int +0.8%, table_concat +0.3%, array +0.2%), each
  still well under the reference's peak.
- spectral_norm reads 2.2% slower (p=0.019, ±9%); it creates no string in
  its loops, and its loop code is unchanged. Treated as layout; the final
  comparison against the reference shows where it stands.
