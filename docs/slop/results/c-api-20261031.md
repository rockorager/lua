# The C API prototype's costs, 2026-10-31

What turning on `-Dc-api=true` costs, against reference C Lua 5.5.1 (the
dev shell's `lua`) and our default build. The design is `../c-api.md`.
Machine: the orb's 4-core Intel Xeon @ 2.60GHz, runs pinned to core 3
with `taskset`, rounds interleaved, benchstat. Builds are ReleaseFast.

## Headline

|                                        |       reference | default build |                   C-API build |
| -------------------------------------- | --------------: | ------------: | ----------------------------: |
| bench/ wall time, geomean vs reference |               0 |        −23.0% | −18.7% / −22.7% (two layouts) |
| bench/ peak RSS, geomean vs reference  |               0 |        −37.8% |                         −4.9% |
| peak RSS of `lua -e ''`                |        2.62 MiB |      1.49 MiB |                      3.02 MiB |
| startup, `lua -e ''`                   |         1.34 ms |       0.80 ms |                       1.29 ms |
| call of an empty C function            |          6.1 ns |             — |                       15.2 ns |
| C → `lua_call` → Lua and back          |         33.2 ns |             — |                       63.3 ns |
| native stack per C → Lua level         |           351 B |             — |                        1903 B |
| lua-cjson decode+encode loop           | 0.90 s, 3.7 MiB |             — |               0.82 s, 4.5 MiB |
| lpeg match loop                        | 0.37 s, 2.9 MiB |             — |               0.34 s, 3.2 MiB |

Lua code stays faster than the reference with the C API on; the gap to
the default build is within the loop's layout noise. Memory does not
stay leaner on small programs: the dynamic glibc the C API needs costs
1.3 MiB of mapped pages, which puts the floor 0.4 MiB above the
reference's. Calls into C cost 2.5× the reference's per call, which
matters only for code that is mostly tiny C calls; the two real rocks
measured still run faster than on the reference.

## The default build is unchanged

- Both `vm.runLoop` instances of the default ReleaseFast build are
  byte-identical to a4deed2's with addresses masked (0x7dee and 0xa046
  bytes; `objdump -d --no-show-raw-insn`, addresses, symbols and
  `__anon` suffixes masked as in `safe-poison-20261031.md`). The whole
  `.text` section of the default build is identical between the branch
  head and the build benchmarked below.
- It is still static and libc-free (`file`: statically linked).
- bench/, 10 rounds: base (a4deed2) −23.19% against the reference,
  default (this branch) −22.95%; peak RSS −37.82% and −37.84%. Level.

Reading it:

- **Time.** `capi` and `capimalloc` run the same interpreter code, and
  their time differs by up to 18% on single programs (globals 883 ms
  against 749 ms, steady over repeated runs) where neither allocates in
  its loop. That is code placement, not the allocator, and it brackets
  the C-API build at −18.7% to −22.7% against the reference, with the
  default at −23.0%.
- **Code generation.** The C-API loop is not the default's: Zig builds
  code that links glibc dynamically position-independent and refuses
  `-fno-PIC` there ("the selected target requires position independent
  code"), even though `lua` itself is a non-PIE `EXEC`. The loop then
  keeps the jump table's base in a register (`lea table(%rip),%r13`;
  `jmp *(%r13,%rax,8)` instead of `jmp *table(,%rax,8)`): one register
  fewer for the loop, 0x8042 bytes instead of 0x7dee. Getting non-PIC
  code back would need a non-glibc libc or Zig's rule relaxed.
- **Allocators matter for memory.** glibc malloc costs peak memory on
  every allocation-heavy program: array 35.8 MiB against 22.4,
  table_concat 34.8 against 24.5, binary_trees 33.0 against 28.1,
  hash_int 8.9 against 7.4, json 13.5 against 11.9; geomean +0.9%
  against the reference where ours is −4.9%. Its time is level with
  ours. Keep our allocators in the C-API build.
- **The floor dominates the small programs.** Every program under
  4 MiB peaks at 3.05 to 3.44 MiB on the C-API build, 3 to 9% above the
  reference, against 1.5 to 1.9 MiB on the default build.

- The C API's own cost is glibc and the dynamic loader: ~1.3 MiB the
  static build does not map. The reference pays that too, plus libm and
  ncurses; what keeps us above it is our executable's text, 1.3 MB
  against 300 KB, of which 876 KiB is resident after startup.
- 256 KiB of the anonymous memory, in both of our builds, is Zig's
  per-thread alternate signal stack (`std.options.signal_stack_size`,
  `Thread.maybeAttachSignalStack`), in TLS. With
  `std_options.signal_stack_size = null` in `main.zig` (a temporary
  edit, reverted): default 1280 KiB, C-API 2788 KiB. Not changed here:
  it removes std's segfault stack traces, which is the owner's call, and
  it would help both builds alike.

  `lua` links libm. Ours has its own math and does not, so a library
  that fails to `dlopen` is retried once after `libm.so.6` is opened
  with `RTLD_GLOBAL`. Only such a library pays libm's 400 KiB: lpeg
  costs 84 KiB on ours (56 on the reference), cjson 764 KiB.
- glibc malloc instead of our allocators saves 32 KiB at the floor.

### Measuring peak RSS

`just bench-compare` runs `time -f %M taskset -c N lua`. ru_maxrss keeps
its high-water mark across exec, so every arm's peak RSS is at least
taskset's own, 2376 KiB (`time taskset -c 3 /bin/true`). The default
build's "2.38 MiB floor" in earlier write-ups is taskset's; the
default build's own is 1.5 MiB. Programs above 2.4 MiB are measured
correctly. `just bench-capi` runs time under taskset; `bench-compare`
is left as it is for comparability with earlier waves.

Subtracting the empty loop (4.1 and 4.7 ns): a call of an empty C
function is 15.2 ns on ours and 6.1 ns on the reference; `add` 32.7
against 21.7; `callback` 63.3 against 33.2.

Where the 15 ns goes (`perf record`, nop): the interpreter's native
call path (`vm.preCall`, `vm.callNative`, part of `runLoop`), which any
Zig native pays too, and the trampoline with `jmp.call` (26% of samples):
the frame's closure load, the thread-local `current` save and restore,
the eight register saves, the result check. A Zig native that does as
little (`coroutine.isyieldable`) costs ~9 ns on ours and ~10 on the
reference, so about 5 ns of the 9 ns gap is the trampoline and the rest
our native call path against the reference's direct `precallC`.

The trampoline's first version stored its `Error!u32` result through a
stack temporary written in two parts (the 2-byte error, the 4-byte
value) and read in one 8-byte load, a store-forwarding stall on every
call. Inlining the cold failure path into the trampoline let LLVM write
the result in place: nop went from ~16 to ~15 ns. A tail call to the
failure path does not compile (LLVM's musttail cannot pass the `sret`
result), and two other shapes kept the stall.

`add` adds three API calls of ~1 ns each over the reference's: every
`lua_*` and `luaL_*` call from a module goes through the PLT on both.

## Native stack

`calls.lua stack 100`: bytes of native stack per level of
Lua → C (`callback`) → `lua_call` → Lua. 1903 on ours, 351 on the
reference. `runLoop`'s own frame is 1432 bytes of it (`sub $0x598,%rsp`
plus pushes), the trampoline and `jmp.call` ~160, `lua_callk` and
`vm.call` the rest. A C module that recurses through `lua_call` hits the
C-stack limit (`LUAI_MAXCCALLS`, 200 levels) at ~380 KiB against
~70 KiB, well inside an 8 MiB main stack; threads with small stacks
would feel it. The fix is in `runLoop`'s frame, not in the C API.

## Startup

`perf stat -r 300 -e task-clock lua -e ''`:

```
reference  0.92 msec task-clock   1.344 ms elapsed (± 1.79%)
default    0.47 msec task-clock   0.805 ms elapsed (± 1.42%)
C-API      0.92 msec task-clock   1.293 ms elapsed (± 0.96%)
```

Dynamic linking (ld.so's relocations and glibc's initialization) costs
the C-API build the 0.5 ms the static build saves; it ends level with
the reference. Loading a module: `require "lpeg"` 1.245 ms on the
reference and 1.380 on ours, `require "cjson"` 1.330 and 1.479 (the
second includes the failed first `dlopen` and libm).

## Real modules

The same `.so` files on both, built against `zig-out/include`.

- lua-cjson: decode and re-encode a 200-element array of objects 2000
  times: 0.80–0.85 s and 4.56 MiB on ours, 0.87–0.93 s and 3.6–3.7 MiB
  on the reference (3 runs each).
- lpeg: a comma-separated word list matched 300000 times into a table:
  0.34–0.35 s and 3.24 MiB on ours, 0.37–0.38 s and 2.87 MiB on the
  reference.

Both spend most of their time in C and in table and string work done
through the API, and still finish ~9% faster than the reference; the
extra memory is the floor (and libm for cjson).
