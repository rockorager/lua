# Wave 11: io as `luaL_Stream`, `dlclose`, aarch64, 2026-10-31

What the C API's io on C's stdio, `dlclose` with the state, and the
aarch64 trampoline cost, and the proof that the default build did not
move. The design is `../c-api.md` ("io handles are `luaL_Stream`", "C
libraries close with the state", "aarch64"). Machine: the orb's 4-core
Intel Xeon @ 2.60GHz, runs pinned to core 3 with `taskset`, rounds
interleaved, benchstat. Builds are ReleaseFast. Base is b647dab.

## Headline

- The default build is unchanged: `vm.runLoop` byte for byte, `.text.hot`
  and `.text` the same sizes, bench/ level with base (+0.30% time, −0.02%
  peak RSS, every row `~`).
- The C-API build's io is the reference's code on the reference's libc.
  Against the previous C-API build, whose io was the default build's Zig
  io, it is slower and a little larger on every io workload, and still
  faster than the reference on all but `read("a")`: geomean −18.4%
  time and −12.3% peak RSS against the reference, where the old io was
  −37.0% and −18.9%.
- Startup is level; the floor is 48 KiB higher (1952 against 1904 KiB),
  C stdio's buffers and liolib's code.

Reading it:

- **Why slower than the Zig io.** Every io function is now a C function
  calling the C API: arguments come through `lua_tolstring`,
  `luaL_checkinteger` and friends instead of direct `Value` access, and
  results through `luaL_Buffer` and `lua_pushlstring`. In `print`
  (`io.write` with four arguments) `lua_tolstring` alone is about a
  quarter of the time; most of it is a store-forwarding stall where
  capi's `get`/`at` return a `?Value` through memory. The rest is glibc's
  stdio, which is what the reference pays too.
- **`read("a")`, the one loss.** The reference reads a whole file into a
  `luaL_Buffer` whose box `realloc`s, which glibc does in place with
  `mremap` for large blocks. lauxlib's box grows by allocating a new
  userdata of 1.5× and copying, and the old ones wait for the collector.
  As a straight port, `read("a")` of 20.6 MB took 560.8 ms against the
  reference's 181.2 ms (+209%) and peaked at 107.7 MiB against 63.3. So
  `readAll` sizes the buffer to the rest of a regular file first (`statx`
  on Linux), one allocation instead of ~25: 286.5 ms, +50%, and the
  reference's memory. What is left is a fresh 20 MB box per read (page
  faults the reference's reused, `mremap`ped block does not take) and
  the copy into the string, which the reference also makes.
- **Memory.** 0.15 to 0.34 MiB more than the old io on the small
  workloads, still 13 to 17% under the reference. Not broken down yet.

Before the presizing, same script, same machine, 10 rounds: `all`
560.8m ± 7% and 107.71k ± 0% (geomean time 188.9m, −5.00% against the
reference; RSS 5.437k, −2.43%).

  qemu-user 11.1.2, against nixpkgs' aarch64 `lua5_5` (io_os against the
  native reference; see `c-api.md`).

  (checked by editing one out, reverted).

  are identical masked to base's C-API build (15,754 lines each;
  `@alignCast` on a function pointer compiles to nothing on x86-64).
