# NaN-boxing against the 16-byte tagged value, 2026-10-31

Plan decision 1 started with PUC-Rio's 16-byte value (an 8-byte payload
and a 1-byte tag) and asked to measure NaN-boxing, which halves a value
to 8 bytes but has no room for all of Lua 5.5's 64-bit integers.

## The prototype

A prototype on 124cb08 replaced `Value.zig`'s representation and
everything that reached past it (`Table.zig`'s nodes and array part,
`gc.zig`'s table traversal, the field reads in `vm.zig` and the
libraries). It was built to measure, not to land, and it gives
NaN-boxing every advantage a complete version could have:

- **Encoding.** A float is its own bits. Anything else is a quiet NaN
  with the 13 high bits set, a 4-bit tag code in bits 47..50, and a
  47-bit payload: pointers (x86-64 user space fits 47 bits), booleans,
  nil, and integers in [−2^46, 2^46). Tag code 0 is the float region,
  so x86's default NaN (0xFFF8000000000000) and ARM's (0x7FF8...) are
  floats. `Value.float` canonicalizes any NaN that would land in the tag
  region (from `string.unpack` or `undump`); the VM's float arithmetic
  skips that check, since the hardware only produces its default NaN or
  propagates an operand's.
- **Type checks** are one shift and compare (`bits >> 47 == tag`), a
  float check is one compare against a constant, and `nil`/`false` are
  one subtract and compare. The VM's fast paths use those, not a decoded
  tag.
- **Integers beyond 47 bits** went to a leaked process-wide list, tagged
  `big_int`, standing in for the heap box a complete version needs. Every
  integer result checks that it fits (`fitsSmall`: shift, shift back,
  compare) and calls a cold function when it does not, which is what
  a complete version's fast path would also do. `FORLOOP` assumes its
  count and index fit; a complete version would choose a slow loop in
  `FORPREP`.
- **Tables.** A node is the value's bits, the key's bits, and `next`,
  4-byte aligned: 20 bytes instead of 24 (an 8-aligned node is 24 bytes
  again). Key identity is one 64-bit compare. The array part is 8 bytes
  a slot instead of 5.5's 9, with no tag run.
- **Stack, constants, upvalues, native closure upvalues**: 8 bytes a
  value instead of 16.

Every `bench/` program printed the reference's checksum on the
prototype. format.lua multiplies past 2^47 (`i * 2654435761`), so it
also exercised the big-integer path.

Base is 124cb08; nanbox is the prototype. ReleaseFast, 10 rounds of
every `bench/` program, interleaved, pinned to the last core, wall time
and peak RSS per process, benchstat.

## Reading it

Time: 7.1% slower on the geomean, and slower on every program that
spends its time in the interpreter loop except coroutines.

- fib +15%, methods +15%, globals +14%: integer compares and arithmetic
  now unpack the payload (shift left, shift right) and repack the result
  after a range check, and every switch over a value's type (calls,
  `__index` chains, the slow paths) decodes the tag first.
- mandelbrot +20%, spectral_norm +22%: a float check is a 64-bit
  immediate load and compare, and a float moves between a general and a
  vector register at each load and store; the 16-byte value compared a
  tag byte in memory and loaded the float straight into a vector
  register.
- coroutines −12%: each coroutine's stack is half the size to allocate
  and clear. patterns −2.4%.

Peak RSS: 9.2% higher on the geomean. The value got smaller, but the
benchmarks' memory is mostly in tables, and 5.5's compact array part
already stores 9 bytes a slot.

- hash_int −13%, binary_trees −3%: the 20-byte nodes.
- array +25%, table_concat +22%: a growing array part must write nil
  (8 bytes) into every new slot. The compact layout writes one tag byte
  per slot and leaves the payload pages of capacity not yet used
  untouched, so they never count in RSS.
- hash_string +41%: Lua's own count (`collectgarbage("count")`) ends 7%
  lower on the prototype, so the extra RSS is outside the objects. A
  variant with 8-aligned 24-byte nodes peaked at the base's 22.8 MiB in
  a single run; I did not pin down whether the collector's pacing or
  the allocator moves the peak with the 20-byte size.
- format +125%: the prototype's leaked list of 500,000 big integers.
  A complete version would allocate and collect a box per overflowing
  multiply instead, which is what the hot-path rule forbids
  ("allocate on an instruction's path only where the language
  allocates").

## Decision

Keep the 16-byte tagged value. NaN-boxing loses on time even with
every shortcut a complete version could take, and it does not win peak
memory on these programs. A complete version would cost more again:

- `Value.int(i64) Value` cannot represent every integer without a heap,
  so every integer constructor in the libraries and the embedding API
  would take the state and could fail, and integer arithmetic would
  allocate.
- Light userdata would be limited to 47-bit pointers.

What the prototype did show is where the 16-byte value costs memory:
stacks and coroutines. If coroutine-heavy programs become a target,
that is the place to look, not the value.
