# Threaded dispatch against a plain switch, 2026-10-31

Plan decision 3 asked to measure once what the labeled `switch` with
`continue :dispatch` buys over a plain loop around a `switch`.

## The arms

- **base**: 124cb08 (origin/main), `runLoop` as it is: every prong ends
  in `continue :dispatch try nextOp(...)`, which Zig compiles to one
  indirect jump per prong. `objdump` counts 340 indirect jumps across
  the loop's two instances (unhooked and hooked).
- **plain**: the same source with the switch inside `while (true)`, and
  every `continue :dispatch EXPR` rewritten to `next_op = EXPR;
continue :dispatch;`, which jumps back to the one switch at the top.
  LLVM did not tail-duplicate it back into threaded code: 5 indirect
  jumps across both instances. Nothing else changed.

ReleaseFast, 10 rounds of every `bench/` program, interleaved, pinned to
the last core, wall time and peak RSS per process, benchstat.

## Reading it

- Threaded dispatch is 9.0% faster on the geomean, and no program is
  significantly faster plain. The programs whose time is the interpreter loop gain
  most: mandelbrot 33%, array 17%, nbody 15%, spectral_norm 13%,
  coroutines 12%, fib 11%, closures 10%. The programs whose time is in
  the libraries (concat, format, patterns, table_concat) do not move.
- Peak RSS is level; the plain loop's smaller code saves under 0.5% on
  a few programs.
- Decision 3 stands: the labeled switch with `continue :dispatch`.
